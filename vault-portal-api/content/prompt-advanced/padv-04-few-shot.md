"给例子"是提示词工程里性价比最高的技术（本站通识库第 3 篇）。但"贴两个例子"和"示例工程"之间差着一整个方法论：例子选不对，示范效果为零甚至为负。这一篇讲透选、排、量三个维度。

## 选：多样性与代表性

**一个黄金标准：示例集合要覆盖任务的"决策边界"。** 常见失误是示例全是"标准情况"——模型学到的只是"平均情况的处理"，边界全靠自由发挥。覆盖清单：

1. **常规正例**：任务的标准形态（2-3 个）；
2. **边界正例**：容易误判的情况（歧义表述、嵌套结构、少见的合法输入）；
3. **反例/拒绝样本**：**最常被遗漏**——"这个输入不属于该任务/答案应该是 X 因为信息不足"的示例，教会模型说"不"；
4. **易混淆对**：两个长得像但答案不同的输入放一起（"退货申请" vs "换货申请"），决策边界被显式划出。

数量起步：3-6 个，覆盖比数量重要——6 个同质示例不如 3 个异质示例。

## 排：顺序与格式的影响

模型对示例的利用有两个已知偏差，工程上要顺势而为：

1. **近因偏好**：排在最后的示例影响最大——把**最典型、最重要的示例放最后**，边界情况放中间；
2. **格式一致性**：示例之间的格式必须严格统一（同样的字段顺序、同样的标点风格）——模型会把示例的格式当作输出格式的权威定义，不一致的示例 = 自相矛盾的规格说明。

另外两个细节：示例与真实输入之间用**固定分隔符**（如 `###` 或 XML 标签）隔开，避免模型把示例当对话历史；示例的"答案部分"要完整到可直接验收（含模型该有的所有字段），半成品示例教出半成品输出。

## 动态示例检索：让系统自己选例子

固定示例集对千变万化的输入总有覆盖不到的角。进阶做法（与 RAG 同构）：

1. 把示例库向量化（每条 = 输入+理想输出）；
2. 用户输入到来时，检索**最相似的 K 条**示例注入提示词；
3. 相似输入 → 相似示例 → 模仿质量最高。

这就是"动态少样本"（很多 RAG 框架的内置能力）。它把"选例子"从手工活变成检索工程，例库随 bad case 持续积累——你的示例库变成会成长的资产。注意：检索出的示例仍要保证格式一致与总量克制。

## 什么时候"给例子"不划算

三个信号说明该换方法：

- **示例库已经膨胀到不可维护**（几十条、占掉大量输入 token）→ 结构化任务转微调（本站本地部署库第 9 篇），示例集就是现成的训练数据；
- **规则本身可以明说**：能写成清晰规则的不要用例子暗示（"日期一律 ISO 格式"直接写，比三个例子含蓄表达强）——**规则说规律，示例教边界**，两者分工；
- **任务在语义上根本模糊**：示例救不了定义不清的任务，先回去把任务定义写清楚。

## 与提示词其他部分的配合

- 示例与 schema（第 3 篇）配合：schema 定字段，示例定"好答案的样子"，两者不一致时模型会懵——**以示例为准改 schema，或反之，必须二选一对齐**；
- 示例与 CoT（第 2 篇）配合：示例里展示推理过程（不只展示答案），教的是"怎么想"而不只是"想成什么样"。

## 小结

示例工程 = 覆盖决策边界的选例（含反例）+ 近因排序 + 严格一致的格式 + 按需检索的动态化。把示例库当资产管理，它会成为系统里最稳定的"行为定义"。下一篇：系统提示词的组织与维护——当指令多到成文档。
