切好的 chunk 要变成向量才能被"语义检索"。这一篇讲两件事：Embedding 模型怎么选，向量数据库要关注哪些能力。

## Embedding：把语义变成几何

Embedding 模型把一段文字映射成高维空间中的一个点。训练目标让"意思相近的文本"在空间里彼此靠近——于是"如何申请报销"与"差旅费用流程"虽然字面不同，向量距离却很近。检索就是：问题转向量，找库里最近的 K 个点。

关键认知：

1. **同一个模型管输入和输出**。查询和文档必须用同一个 Embedding 模型向量化，换模型 = 全库重建索引。
2. **模型有"擅长语言"和"擅长领域"**。中文场景优先在中文/多语基准上验证过的模型；医疗、法律等垂直领域，通用模型的相似度判断可能失灵。
3. **它是"相似度"不是"等价度"**。向量近代表话题相近，不代表能回答——"报销制度"和"报销被拒的吐槽"可能很近。这就是需要重排（第 7 篇）的原因。

## 选型看什么

| 维度 | 说明 |
| --- | --- |
| 检索质量 | 在 MTEB / C-MTEB 等基准与自己的评测集上的表现（评测集优先，见第 9 篇） |
| 语言支持 | 中文/中英混合的召回质量，亲自用真实 query 试 |
| 维度 | 维度越高表达力越强，但存储与计算成本越高；现代模型 1k 左右维度已够用 |
| 长文本支持 | 模型单次能编码的最大 token 数，短于你的 chunk 长度会截断 |
| 部署形态 | API（省心、数据出域）vs 开源自部署（可控、合规），商业敏感场景优先后者 |
| 成本 | 向量化是批量任务，全库+增量更新都要过一遍模型，单价乘库容先算一遍 |

经验：先用当期的主流开源模型（如 BGE 系、GTE 系、各厂商新发布的 embedding 模型）+ 评测集盲测；质量过关再谈更复杂的。

## 向量数据库能力清单

选型关注的不是"快"（都很下功夫），而是这六项工程能力：

1. **元数据过滤**：按来源/日期/部门/密级过滤后再算相似度——权限隔离（第 13 篇）的基石，必须有。
2. **混合检索支持**：向量 + 关键词（BM25）双路索引原生支持最省事（第 5 篇）。
3. **规模与成本曲线**：百万级以下，pgvector/SQLite 级方案就够；亿级再谈专用向量库的分布式能力。**别为想象中的规模买单。**
4. **更新与删除**：文档修订后按来源删除旧 chunk 的能力，数据更新（第 13 篇）依赖它。
5. **多租户/命名空间**：不同部门/租户索引隔离。
6. **运维成本**：自托管 vs 云服务；团队没有专职运维时，托管或"数据库插件"形态（pgvector）显著降低心智负担。

## 起步配置建议

一个务实的起点组合：**Postgres + pgvector（单库搞定元数据过滤+向量）+ 主流开源 embedding 模型**。它能陪你从原型走到相当大的规模，等真实瓶颈出现（通常是检索质量而非性能）再升级组件——届时你已经有评测集，换任何组件都有据可依。
