检索质量的天花板，往往卡在一个容易被忽略的环节：**拿去检索的 query 就是用户敲的原话**。用户问"那个东西坏了怎么修"，语料里写的是"设备故障排除指南"——字面与向量都对不上。查询改写（Query Transformation）就是在用户与检索库之间加一层"翻译"。

## 四类技术

**1. 改写（Rewrite）：把口语变书面。** 用一个小模型把口语化、有错字、指代不清的输入改写成适合检索的规范表述。"上次那个事后来咋样了"→ 结合对话历史改写成带主体的完整问题。对话式产品必备——**多轮对话的指代消解**是改写的第一个应用：用户第二句问"那价格呢？"，直接拿去检索必挂。

**2. 扩展（Multi-Query）：一问变多问。** 让模型从不同角度把问题改写成 3-5 个变体，各自检索后合并结果。价值在覆盖语料的多种表述方式；代价是检索成本翻倍。适合高价值低 QPS 的场景。

**3. 分解（Decomposition）：复合问题拆子问题。** "对比 A 和 B 的价格与保修政策"→ 拆成"A 的价格""B 的价格""A 的保修""B 的保修"四个子查询，分别检索后再汇总作答。识别信号：问题里有"和/与/对比/分别"。

**4. HyDE：先编一个假设答案再去搜。** 让模型先生成一段"假设性回答"，用它的向量去检索——因为答案与答案在向量空间更相近（文档是陈述句，问题疑问句），命中率常高于拿问题本身去搜。代价是多一次生成调用，且假设答案错了会带偏方向，需要配合重排兜底。

## 决策速查

| 信号 | 优先用 |
| --- | --- |
| 多轮对话、指代频出 | 改写（含历史压缩） |
| 命中率低、换问法就能搜到 | Multi-Query 扩展 |
| 问题包含多个并列对象 | 分解 |
| 问题与文档"文体差异"大（口语 vs 书面） | HyDE |

## 三个工程注意

1. **改写用小而快的模型**，别用旗舰模型——这一步只要忠实转述，不要创作，便宜模型的延迟优势巨大。
2. **保留原 query 一路**：改写再好也可能丢原始关键词（型号、人名），混合检索里始终保留"原话直查"这一路。
3. **改写质量也要评估**：把评测集（第 9 篇）的 query 先过改写层再检索，对比命中率变化——任何一层优化都要能被测出来，否则就是在猜。

## 小结

查询改写是"花小钱办大事"的典型：一次便宜的模型调用，常常带来两位数的命中率提升。但它增加延迟与成本、引入新的失败点，**先测出检索侧的真实瓶颈**（第 10 篇的诊断清单）再决定上哪一层。
