"一个 Agent 不够就上多个"——多智能体是 Agent 领域最容易被滥用的模式。拆分得当，系统获得隔离性与并行性；拆分不当，你得到的是"会互相传话的 API 账单"。这一篇讲什么时候拆、怎么编、怎么通。

## 先问该不该拆

拆分的正当理由只有三个：

1. **上下文隔离**：不同子任务的工具集与资料差异巨大（研究 Agent 的 20 个检索工具 vs 写作 Agent 的文档模板），拆开后各自上下文干净、工具选择准确率高。
2. **并行加速**：子任务独立可并行（同时调研三家竞品）。
3. **独立迭代**：子能力有独立的质量与发布节奏（评审 Agent 单独优化不影响主流程）。

**不该拆**的信号：子任务其实是一个顺序流程（一个工作流节点就够）；拆分后两个 Agent 需要共享 90% 的上下文（通信成本大于隔离收益）；纯为了"多智能体"的架构时髦。一个朴素的对照：多数成功的生产系统是"一个强 Agent + 若干工具"而非"一群会话 Agent"。

## 四种编排拓扑

**1. 主管模式（Supervisor）。** 一个编排 Agent 接需求、拆任务、派发给专职 Agent（研究/写作/数据），收结果汇总。**最常用**：职责清晰、控制点集中、易审计。要点：主管的拆解质量决定一切（第 2 篇规划），专职 Agent 的工具面要窄。

**2. 流水线（Pipeline）。** A→B→C 固定顺序（解析→分析→成稿），每站专注一站。可预测、可单测，适合流程稳定的文档/数据处理。

**3. 辩论/评审（Debate/Review）。** 生成者与评审者对抗（写代码→代码评审→修改→再审）。单 Agent 自审容易"自己惯自己"，独立评审者用新鲜上下文挑错，收益明显。成本是轮数与延迟，通常 1-2 轮足够。

**4. 群聊（Group Chat）。** 多 Agent 自由发言。学术上有趣，工程上最难控——轮流顺序、话题漂移、成本失控。除非任务确实开放（头脑风暴），生产慎用。

## 通信：共享黑板优于点对点闲聊

Agent 之间的"对话"如果不加设计，很快变成互相转述的噪音。工程上的标准解法是**共享黑板（shared state）**：

- 中间产物（文件、数据表、结构化报告）写入共享存储，消息里只传**引用与摘要**——避免大段内容在 Agent 间来回转述失真（每转述一次都是一次有损压缩）；
- 每个产物有 schema（谁产出、给谁、字段含义），下游才能稳定消费；
- 通信消息尽量结构化（任务书：目标/约束/交付物/完成标准），而非自然语言闲聊。

## 两个工程红线

1. **总控必须收口**：无论哪种拓扑，要有一个可确定的"结束条件与产出出口"——最终答案由谁合并、以什么标准验收。多智能体系统最常见的故障是"都在动，没人负责收"。
2. **预算与深度封顶**：主管可以派工，专职 Agent 又能再派工——递归深度和总 token 预算要有硬上限，否则一次误解的任务书会指数级放大成账单。

## 调试视角

多智能体的排障原则：**先看黑板，再看对话**。黑板告诉你每个产物的状态与归属（哪一站没交付），对话轨迹告诉你为什么（任务书是否被理解偏）。轨迹可回放（第 7 篇）是多智能体系统的生命线。

## 小结

多智能体的正确姿势：按"上下文隔离/并行/独立迭代"三个正当理由拆，拓扑上首选主管与流水线，通信用共享黑板传引用，总控收口、预算封顶。下一篇进入可靠性段：怎么科学地评估一个 Agent 的好坏。
