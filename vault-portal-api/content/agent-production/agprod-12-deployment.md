前十二篇的能力拼齐了，这一篇谈"装订"：demo 与产品之间差的是什么。答案通常不是更多功能，而是**架构、隔离、发布纪律与迭代节奏**。

## demo 与产品之间的六道鸿沟

1. **并发**：demo 一个会话，产品一百个并发 run——会话隔离、资源配额、队列与限流从第一天就要有；
2. **凭证**：demo 用你自己的 token，产品要有完整的凭证管理（发放/轮换/吊销，第 9 篇）；
3. **可观测**：demo 靠肉眼盯，产品靠轨迹与告警（第 7 篇）；
4. **失败处理**：demo 假设成功，产品假设失败是常态（第 8 篇）；
5. **成本**：demo 不算钱，产品要单位经济学（第 11 篇）；
6. **合规**：demo 没有审计，产品的每个动作要可回溯。

## 架构分层：把"易变的"和"稳定的"分开

一个可持续演进的 Agent 服务，推荐四层：

```
接入层（API/会话管理/鉴权/限流）
  ↓
编排层（Agent 循环/计划/护栏/预算闸）     ← 变化最快
  ↓
能力层（工具服务/MCP/检索/模型网关）
  ↓
资源层（模型 API/数据库/向量库/存储）
```

要点：**模型网关收口所有模型调用**（统一计费、限流、日志、模型切换——换模型供应商只动一层）；**能力层独立部署**（工具服务化，多个 Agent 复用，权限各自收敛）；编排层拥抱变化（提示词、流程、模型配置全部版本化，见下）。

## 发布纪律：提示词也是代码

Agent 产品的"发布物"比传统应用多：提示词、工具描述、流程图、模型版本、评测集。全部进版本管理，全部走发布流程：

- **配置即发布**：提示词与流程配置不做热改——改了没记录，出问题无法回溯是谁改的哪一行；
- **评测门禁**：发布前跑评测集（第 6 篇），关键指标不回退才放行——这是 Agent 版的 CI；
- **灰度**：新版本先放 5% 流量，看完成率/成本/用户信号，再全量；
- **一键回滚**：任何一层都能秒级回上一版（模型行为漂移时这是救命稻草）；
- **模型升级 = 发布**：供应商"静默更新"模型可能导致行为变化，把"锁定模型版本"设为默认，升级按正式发布流程走评测。

## 环境与数据隔离

开发/测试/生产三环境各自的模型配置、凭证、数据集都要隔离；测试环境用合成数据或脱敏数据（第 9 篇红线在开发流程的延续）；评测与演练在测试环境跑，生产的轨迹数据脱敏后回流评测集。

## 团队与迭代节奏

Agent 产品的团队分工有个新角色比例：**运营 bad case 的人**几乎与写功能的人一样重要——每周看聚类报告（第 7 篇）、修工具描述、扩评测集、调护栏。节奏建议：以周为单位收束一轮"bad case → 修复 → 评测回归 → 发布"，月度做一次成本与安全复盘（第 11/9 篇）。

## 里程碑参考

一个务实的"demo→产品"推进序列：单任务跑通 → 评测集建立（此时才叫可迭代）→ 并发与隔离加固 → 观测与告警 → 灰度上线 → 按周迭代。跳过评测集直接上线的 Agent，会在第一个流量高峰后进入不可知状态——那时候补的代价是三倍。
