"我感觉它挺聪明的"不是评估。Agent 比聊天应用更难评——同样的输入可能走出不同轨迹——但正因为不可复现，**评估必须更工程化**，否则每次改动都是赌博。这一篇给一套从单步到端到端的评估框架。

## 三层指标：把"好不好"拆开

| 层 | 评估什么 | 指标举例 |
| --- | --- | --- |
| 单步 | 每次决策对不对 | 工具选择准确率、参数有效率、单步成功率 |
| 轨迹 | 过程合不合理 | 步数、冗余调用率、死循环率、预算达成率 |
| 终态 | 任务完成没有 | 完成率、结果正确率、人工评分、用户满意率 |

分层归因的价值：终态失败时，看轨迹立刻知道是"计划错了"（第 2 步就偏航）还是"执行错了"（计划对、某步工具调用失败）。**只有终态指标的团队，永远在盲修。**

## 评测集与仿真环境

聊天应用的评测集是"问题+标准答案"；Agent 的评测集需要**环境**：

- **任务集**：每个任务定义目标、初始状态、可用工具、完成标准（可程序化判定优于人工判断）；
- **环境隔离**：给 Agent 造一个沙箱环境（测试库、mock API、沙箱文件系统），让它真的动手而不影响生产——评估必须允许它"真实地失败"；
- **对照断言**：不只看最终答案，断言中间状态（"订单必须已创建""邮件不得外发"）——过程断言能抓住"蒙对结果但过程危险"的 case。

冷启动任务集从真实用户任务里选 30-50 个典型（含易混、边界、恶意输入），按难度分层；上线后 bad case 持续入库。

## LLM-as-judge：用法与校准

终态结果常无唯一标准答案（报告写得好不好？），用强模型当裁判是务实选择，但必须校准：

1. **给 rubric**：评分维度明细化（准确性/完整性/格式/语言），每档分数有锚定描述，别让裁判自由发挥；
2. **给参考**：提供人工写的参考答案或要点清单，裁判做"对比评分"而非"凭空评分"；
3. **抽查对齐**：抽样 10-20% 人工复核，确认裁判与人类的分歧率在可接受范围；分歧集中的维度回去改 rubric；
4. **警惕裁判偏置**：偏爱长答案、偏爱自家风格、位置效应——评分时随机化顺序、长度截断。

## 不可复现怎么办

温度与随机性导致同输入不同输出，评估要吸收这一点：

- **关键任务多次采样**：同一任务跑 3-5 次，看通过率的分布而非单次结果；
- **低温不是万能**：生产可以调低温度，但评估环境应与生产一致，否则指标失真；
- **回归基线**：每次改动跑同一任务集，与上版对比通过率——哪怕绝对值波动，相对变化是可信的。

## 一个常见的优先级错误

新手把 90% 的评估精力放在"答案质量"（端到端）；老手先保"单步与轨迹"——因为单步指标便宜（可程序化断言）、稳定（不依赖裁判）、归因清晰。端到端 judges 用在发布前的把关，日常迭代靠单步回归撑。

## 小结

评估体系 = 三层指标 + 沙箱任务集 + 校准过的裁判 + 回归流程。它不是上线后的选修，而是与功能同步建设的基础设施——下一篇的可观测性，就是评估体系在生产侧的延伸。
