Agent 的能力上限 = 模型的推理能力 × 工具的质量。实践中后者被系统性低估：同一个模型，换一套设计良好的工具，成功率可以从"经常出错"变成"稳定可靠"。本站《MCP 从零到一》第 3 篇讲过工具描述的写法；这一篇站在 Agent 系统的视角，讲工具集的整体设计。

## 核心原则：模型是"能力有限的新员工"

为人类写 API 文档，可以假设读者会读手册、会抓包调试、会举一反三。模型不会。它只看得到：工具名、描述、参数 schema、上一次调用的返回。所以：

1. **一次调用必须自包含**。人类 API 可以"先调 A 拿上下文，再调 B 用上"；Agent 多一次依赖就多一分错——能用一个调用完成的，不要拆成两个。
2. **错误要能自愈**。模型收到错误后只有一次修正机会（通常）。错误信息必须包含"哪里错了 + 正确格式长什么样"：`"日期格式错误，应为 YYYY-MM-DD，例如 2026-09-14"`——这让下一轮调用大概率修正；裸异常则直接终结。
3. **返回值是给模型读的，不是给人看的**。截断要声明（"共 340 行，显示前 50 行，用 offset 翻页"）、字段要自解释、大结果要摘要化——模型的上下文是稀缺资源（第 10 篇）。

## 动作粒度：把"业务动作"封装成工具

与 MCP 篇的结论一致但更强调安全维度：

- ✗ 给 Agent `execute_sql(sql)`——它可以 DELETE。
- ✓ 给它 `search_orders(filter)` / `refund_order(order_id, reason)`——动作有业务含义、可枚举、可审计。

把能力收窄到**业务动作层**，有三个收益：模型的调用准确率高（语义清晰）、权限可控（每个动作独立鉴权）、审计有意义（日志里是"退款了订单 X"而非"执行了 SQL"）。必要时留一个受限的"兜底原子工具"，但默认路径永远是业务动作。

## 防呆设计：假设模型会手滑

- **枚举化**：`status: "open" | "closed"` 好过自由文本；
- **危险参数二次确认**：`confirm: true` 显式传入才执行删除类动作；
- **范围限制内置**：查询工具强制 LIMIT、文件写入限制在指定目录（服务端钳制，不靠提示词）；
- **幂等键**：外发/支付类工具支持幂等键，重试不会双发——Agent 的重试是常态，不是异常。

## 工具集的整体架构

一个生产 Agent 的工具集通常分三层：

| 层 | 内容 | 例子 |
| --- | --- | --- |
| 领域工具 | 业务动作，强类型、强约束 | `create_order`、`refund_order` |
| 信息工具 | 检索与查询 | `search_docs`、`get_customer_profile` |
| 通用工具 | 文件、代码执行、浏览器等 | 谨慎授予，沙箱化 |

集成方式上，MCP 已是默认选项（发现、描述、执行全部标准化，本站有专库）；自研场景至少要保证工具 schema 的描述质量与 MCP 同级。

## 一套工具验收法

工具写完不要直接上线，跑一遍"模糊指令测试"：用 10 个真实用户会说的话（含错别字、代词、省略），看模型能否**选对工具、填对参数、在出错后按错误信息自愈**。三个环节全过的工具才算合格。再配一个"歧义测试"：两个工具的描述放一起，让另一个模型判断"该用哪个"——判断不清的就是边界没切干净。

## 小结

工具设计的全部心法：**把模型当成聪明但字面理解、会手滑、没有记忆能力的新员工，用接口设计而不是提示词去兜住它**。下一篇：这个新员工的"记性"——记忆系统。
