本站《AI Agent 从零实战》教你用框架把 Agent 跑起来；这一库往深一层：剥掉框架的外衣，看清 Agent 的本质结构——这样你在选框架、调 bug、做架构决策时才知道自己到底在改什么。

## Agent 的最小定义

剥到最简，一个 Agent 就是这个循环：

```
状态 = 初始任务描述
while 未完成:
    动作 = LLM(状态, 可用工具清单)     # 模型决策
    结果 = 执行(动作)                  # 真实世界
    状态 = 状态 + 结果                 # 累积上下文
```

所有 Agent 框架——LangChain/LangGraph、各家 SDK、自研循环——都是这个循环的不同封装。区别只在三处：**控制流怎么定**（谁决定循环怎么走）、**状态怎么管**（上下文放什么、放不下怎么办）、**工具怎么接**（发现、调用、鉴权）。

理解这一点有两个直接好处：一是任何框架的"魔法"都能还原到这三处；二是调试时你知道去哪看——决策错了看模型层，执行错了看工具层，状态乱了看上下文层。

## 控制流的三种范式

**1. 自由循环（ReAct 风格）。** 模型自己决定下一步：调工具、还是给最终答案。灵活，但长任务容易"绕路"、忘目标、陷入重复。适合步骤不可预知的探索型任务。

**2. 固定工作流（Workflow）。** 步骤预定义：检索→生成→校验，图状结构，分支显式。可预测、可审计、便宜，但遇到计划外情况不会转弯。适合流程稳定的业务任务。

**3. 混合编排（当前主流）。** 大结构用工作流钉死，节点内部用自由循环。比如客服 Agent：整体流程固定（识别意图→查询→答复/升级），"查询"节点内允许模型自由调 3-5 个工具。

经验法则：**能用工作流解决的不要上自由 Agent**。每一点自由度都是成本（延迟、token、不可预测性）。Anthropic 的工程文章把这个观点讲得很透：从固定组合开始，按需增加自主性。

## 状态的三层

| 层 | 放什么 | 生命周期 | 典型实现 |
| --- | --- | --- | --- |
| 上下文窗口 | 当前任务的对话、工具结果 | 单次运行 | 消息列表 |
| 运行时状态 | 计划、中间产物、变量 | 单次运行，可跨窗口 | 图状态/外部存储+索引 |
| 持久记忆 | 用户偏好、历史结论 | 跨会话 | 向量库/数据库 |

新手最常见的崩坏是"什么都塞进上下文窗口"：十轮工具结果之后，窗口被中间产物填满，任务目标被稀释，模型开始忘事。生产级 Agent 必然有**主动的状态管理**：工具结果摘要化、中间产物落盘存引用、定期把"目前进展"重述进上下文——这就是第 10 篇"上下文工程"的主题。

## 框架到底帮你什么

诚实评估框架的价值排序：

1. **工具协议与生态**（MCP、预置连接器）——价值最大，第 3 篇展开；
2. **状态与检查点**（断点续跑、人工审批节点）——生产刚需；
3. **可观测集成**（轨迹记录、回调）——第 7 篇；
4. **抽象掉循环本身**——价值最小，循环只有十行，但抽象层会挡住你看清它的眼睛。

所以选框架的理由应该是前三条，而不是"帮我写循环"。反过来，理解了本篇的解剖图，你也可以判断：哪些场景其实只需要 100 行自研循环 + 一层 MCP，不需要任何框架。

## 本库路线

接下来按"原理→可靠性→生产化"三段推进：规划、工具、记忆、多智能体（设计模式四件套），然后是评估、可观测、失败恢复、安全（可靠性四件套），最后是上下文工程、成本、部署与案例复盘。目标只有一个：让你的 Agent 从"演示能跑"到"凌晨三点不敢宕机"。
