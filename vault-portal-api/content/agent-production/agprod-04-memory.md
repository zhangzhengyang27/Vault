"上次我说过我讨厌等长电话，它这次还是给我转人工排队前最长的一档。"——用户对 Agent 记忆的期待很朴素，工程实现却是最容易做浅的部分。这一篇把"记忆"拆成三层，每层有明确的问题与标准解法。

## 先澄清一个事实

模型本身**没有记忆**。每次调用，它只能看到本次传入的上下文；所谓"记得"，都是工程系统在恰当的时机把恰当的内容塞回上下文。记忆系统的本质是：**决定"什么内容、在什么时刻、以什么形式"进入上下文的策略。**

## 第一层：短期记忆 = 对话历史

最近 N 轮对话直接放上下文——这是默认记忆，也是大多数"记不住"抱怨的来源。两个经典失效：

- **窗口溢出**：聊得够久，最早的约定被挤出窗口。对策：滑动窗口 + 历史摘要（把 20 轮前的内容压缩成几句话钉在系统区）。
- **稀释遗忘**：内容还在窗口里，但隔着几十轮，模型"看不见"它。对策：关键约束（用户偏好、已定决策）在产生时即**提升为持久层**，不依赖对话留存。

## 第二层：工作记忆 = 任务的记账本

Agent 执行长任务时，需要一份"进行时状态"：计划到哪了、哪些事完成了、中间产物在哪。它是**结构化的**（JSON/状态机），不是对话片段：

```json
{
  "goal": "整理 Q3 客户续约名单",
  "done": ["拉取客户列表(312家)", "标记已续约(87家)"],
  "pending": ["按地区分组", "生成汇总表"],
  "artifacts": {"roster": "file://artifacts/roster.csv"}
}
```

要点：中间产物**落盘存引用**（文件路径/记录 ID），上下文里只留引用和摘要——大结果进上下文是长任务崩坏的常见根因；每完成一个里程碑，重述这份记账本（对抗稀释）。这一层在多智能体系统里同时是"共享黑板"（第 5 篇）。

## 第三层：长期记忆 = 跨会话的用户与知识档案

跨会话记忆靠外部存储，两种主流形态：

**1. 语义档案（向量库）。** 会话结束时把值得留的事实抽取出来（"用户偏好简洁回复""项目截止日是 9 月 30 日"），向量化入库；下次会话开始或相关话题出现时检索回填。要点：

- **写入要有门**：不是所有对话都值得记——稳定偏好、事实约定、重要决策才写；琐碎过程写入只会污染检索。抽取时用固定 schema（类别/内容/置信度）。
- **读取要精准**：按当前话题检索 Top-K 注入，而不是"把档案全贴上"。
- **可遗忘**：档案要能更新与删除（用户改了主意、过期信息），否则记忆变成负担。

**2. 结构化档案（数据库）。** 明确的实体属性（用户画像、项目状态）用字段而不是向量——"会员等级 = 金牌"这种事实，向量检索不如一行 SQL 可靠。生产系统通常两者并用：结构化打底，语义检索补盲。

## 反模式清单

- **"全记下来"**：无差别记录一切，检索时噪音淹信号；
- **"记忆必须自动"**：生产环境里，重要记忆让用户可见、可改、可删（"我记得你偏好 X，对吗？"）——透明比神秘可靠，合规上也是要求；
- **"记忆万能"**：记忆解决"重复建立上下文"，不解决能力问题；该写进系统提示词的稳定规则，别指望记忆系统兜住。

## 小结

三层各司其职：对话历史管"这一会儿"，工作记忆管"这一件事"，长期档案管"这个人/这个业务"。设计时先问"这个信息属于哪层、谁在何时需要它"，再决定存与取。下一篇把视角从单个 Agent 抬高：多个 Agent 怎么协作。
