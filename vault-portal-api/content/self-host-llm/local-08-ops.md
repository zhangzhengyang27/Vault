第 6 篇把 vLLM 跑起来了，但要"给团队长期用"，还差运维这一课。推理服务的运维对象很明确：**一个无状态感很强、但资源极其昂贵的服务**——策略都围绕这个特性展开。

## 鉴权与网关

推理引擎自身没有鉴权（vLLM 默认裸奔），必须前置网关：

1. **认证**：API Key 起步（按使用者/应用发 key），企业内网可对接统一身份（OAuth/LDAP）；
2. **限流与配额**：按 key 限 QPS 与日 token 量——推理容量有限，一个失控的批处理任务能吃光整卡，把其他业务全部拖慢；
3. **审计日志**：谁、何时、用了哪个模型、多少 token——成本分摊（第 11 篇）与事件回溯都靠它；
4. **网络边界**：内网部署、HTTPS、不暴露公网（除非走完整的安全网关）。

## 并发治理

- **容量账**：用第 6 篇的压测方法得出安全并发数 C，网关侧把并发上限设在 C 的 80%——留余量给尖峰；
- **排队与超时**：超过容量的请求快速失败或排队（带超时），**别让请求无限堆积**——堆积的内存与用户等待一起崩；
- **业务分级**：给不同业务配不同优先级/独立实例（交互式对话优先，批处理任务用夜间闲时跑）——同一张卡上"一个批处理拖死所有在线对话"是最常见的生产事故；
- **多实例与负载均衡**：容量不够横向加卡加实例，网关轮询。

## 监控指标体系

| 类别 | 关键指标 | 报警建议 |
| --- | --- | --- |
| 服务健康 | 存活探针、错误率、P95/P99 延迟 | 错误率 >1%、P99 超预算 |
| 容量 | 排队请求数、活跃并发、KV 缓存利用率 | 排队持续 >0 视容量告警 |
| 资源 | GPU 显存/利用率/温度 | 显存 >95% 预警 |
| 业务 | 日 token 消耗、按 key/模型分组 | 日消耗异常突增 |

监控之外保留**轨迹日志**（请求参数摘要、模型版本、结果状态）——与 Agent 库第 7 篇同理，出问题先看轨迹。

## 升级纪律

推理服务有两样东西会升级：**模型**与**引擎**。策略都是"像发布代码一样发布"：

1. **灰度实例**：新版本起一个新实例（同机或同集群），网关导 5-10% 流量；
2. **评测门禁**：新旧版本跑同一评测集（第 3 篇的盲测集），关键指标不回退才放量；
3. **快速回滚**：网关切回旧实例，秒级生效——这是实例化部署的最大好处；
4. **锁定版本**：生产永远跑明确版本号，不追 latest（引擎与模型皆然）。

另外两条铁律：**配置变更走变更单**（改参数也是发布）；**驱动/CUDA 这类底层大版本升级放在维护窗口单独做**（最容易翻车的升级）。

## 故障演练

上线前演练四个场景，每个写下恢复步骤：

- 显存 OOM（验证限流与降级）
- 引擎进程崩溃（验证自动重启与探活）
- 上游模型文件损坏/版本错（验证回滚）
- 流量尖峰（验证排队与快速失败）

没有演练过的降级路径，等于不存在。

## 小结

推理服务运维 = 网关收口（鉴权/限流/审计）+ 并发分级 + 四类指标监控 + 版本化升级。这套清单跑顺之后，你的自建服务就已经达到"可以托付业务"的水平了。接下来进入本库的后半场：微调三部曲——真正让模型变成"你的"模型。
