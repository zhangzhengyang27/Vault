MCP 规定了 Client 与 Server 之间的消息格式（JSON-RPC），但消息"怎么传"有不同通道。选对传输方式，决定了你的 Server 是一个本地小工具，还是一个企业级远程服务。

## 两种主通道

**1. stdio（标准输入输出）——本地进程**

Host 把 Server 作为子进程启动，通过标准输入/输出交换 JSON-RPC 消息。

- ✅ 最简单：没有网络、没有鉴权（子进程天然同用户权限）、延迟极低
- ✅ 自动随 Host 启停，本地资源（文件、本地数据库）访问自然
- ❌ 只能本机用；每个用户各自安装运行
- 适合：个人工具、本地文件/开发环境操作、原型验证

**2. Streamable HTTP——远程服务**

Server 作为 HTTP 服务部署，Client 通过 HTTP 请求通信（响应可流式），支持会话管理。

- ✅ 团队/企业共享一个部署：统一更新、统一鉴权（OAuth）、可多租户
- ✅ Server 可以在云端访问它才能到的资源（内部 API、SaaS、专网数据库）
- ❌ 要处理鉴权、传输安全、扩缩容——工程复杂度上一个台阶
- 适合：企业内部统一工具服务、SaaS 化产品、需要集中管控的场景

早期规范还有 SSE 传输；2025 年起的规范以 Streamable HTTP 取代，新实现直接用它。SDK 已把两种通道的切换成本降到很低——**同一个 Server 逻辑，换个启动方式就是另一种形态**。

## 选型信号

| 你的情况 | 选择 |
| --- | --- |
| 个人本地开发工具、读本地文件 | stdio |
| 团队共享、要统一鉴权和审计 | Streamable HTTP + OAuth |
| 连接 SaaS（GitHub/Slack 等）且多用户 | 远程 HTTP + 每用户 token |
| 数据敏感、内网资源 | HTTP 部署在内网，或 stdio + 本地资源 |

## 鉴权的分界

这是两种形态最本质的差异：

- **stdio**：信任边界 = 本机用户。Server 继承你的文件与网络权限，没有"登录"概念。风险（第 9 篇细讲）是提示注入可能借本地 Server 的权限做坏事。
- **HTTP**：必须过鉴权。规范推荐 OAuth 2.1 流程——用户授权后 Server/资源服务器验证身份与权限。企业部署还要考虑：token 生命周期、按租户隔离、审计日志。

一个常见演进路径：**先用 stdio 做原型（一天跑通），验证工具价值后，同一个 Server 逻辑挂上 HTTP + OAuth 变成团队服务**。用 SDK 的情况下，迁移成本主要是鉴权与部署，不是重写。

## 三种典型部署清单

1. **本地个人版**：`npx/uvx` 一键运行的 stdio Server，配置进 Claude Desktop / Cursor 的 JSON 里。第 6 篇动手写的第一个 Server 就是这个形态。
2. **内网团队版**：容器化 HTTP Server 部署在内网，前置网关做 OAuth 与审计，团队所有 AI 工具连接同一个地址。
3. **SaaS 公有版**：多租户 HTTP 服务，每用户 OAuth 授权第三方资源（如替用户调 GitHub），需要细粒度权限与速率限制——这是"把你的产品做成 MCP Server 提供给行业"的形态。

## 小结

传输层选型一句话：**单机用 stdio，共享用 HTTP；本地资源 stdio 拿手，集中管控 HTTP 必须**。搞清形态，下一步就该动手了——下一篇用官方 Python SDK 写出第一个能跑的 MCP Server。
