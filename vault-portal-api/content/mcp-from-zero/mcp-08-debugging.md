MCP 链路横跨模型、Host、Client、Server 四层，出问题时"AI 说不行"的原因可能在任何一层。这一篇给一套系统化的调试方法：先隔离（Inspector），再分层（日志），最后按故障树定位。

## 第一工具：MCP Inspector

官方调试器，一行命令启动：

```bash
uv run mcp dev server.py          # Python SDK
npx @modelcontextprotocol/inspector node build/server.js   # TS SDK
```

它在浏览器里给你一个可交互的协议控制台：

- 看到这个 Server **实际暴露**的所有 Tools/Resources/Prompts（验证注册是否成功）；
- 手动填参数**直接调用**任意工具（绕开模型，验证工具本身）；
- 查看完整的 JSON-RPC 消息流（验证协议交互）。

调试心法：**先在 Inspector 里把每个工具调通，再去 Host 里测**。这样问题要么在 Server（Inspector 里就复现），要么在 Host/模型（Inspector 正常但 Host 异常）——两分法一刀切掉一半排查空间。

## 三层日志

**协议层**（stdio 的 stderr / HTTP 的服务端日志）：连接建立了吗？初始化握手通过了吗？消息是否合法 JSON-RPC？——stdio 模式下任何打印到 stdout 的代码都会污染协议流，这是新手第一坑。

**工具层**：Server 里每个工具调用的入参、返回、耗时、异常。建议统一结构化日志（工具名+参数摘要+结果状态），这是后续一切观测的数据底座。

**模型层**（Host 侧）：模型看到哪些工具描述、决定调用了什么、返回了什么。Host 的 MCP 日志（如 Claude Desktop 的日志文件）能看到协议层报错；自研 Host 则自己埋点。**"模型不用这个工具"的答案在这一层**——九成原因是工具描述弱或参数 schema 吓人（回第 3 篇）。

## 故障树：从症状到根因

**症状 A：Host 里根本看不到我的 Server/工具**
→ 配置文件路径/语法错误 → Server 启动即崩（手动命令行运行看报错）→ 传输参数不对（绝对路径、解释器版本）

**症状 B：工具在，但模型从不调用或乱调用**
→ 工具描述太弱/名字歧义 → 参数 schema 太复杂、必需参数过多 → 工具职责与别的 Server 重叠 → 换更清晰的名字与描述，删冗余工具

**症状 C：调用了但报错**
→ Inspector 单测复现？是：Server 内部逻辑/依赖问题。否：Host 环境（env 缺失、权限、网络）→ 看协议层日志

**症状 D：调用成功但结果"不对"**
→ 参数被模型填错（错误信息是否给出了自愈指引，第 3 篇）→ 返回值被截断/分页未声明 → 语料/数据本身过期

**症状 E：时好时坏、高延迟**
→ 网络抖动/超时未重试 → 工具内部慢（数据库/API）→ 工具太多导致模型决策慢（上下文膨胀）

## 上线前的观测清单

- [ ] 结构化工具日志：每次调用的参数摘要、结果状态、耗时
- [ ] 错误分类计数：按故障树 A-E 归类打点
- [ ] 慢调用告警：超过预算阈值（如 5s）的工具
- [ ] 抽样人工复盘：每周看若干条"模型决策+工具返回"的完整轨迹，持续修工具描述
- [ ] Host/客户端版本记录：协议版本兼容问题要能回溯

调试能力的本质还是可见性——MCP 的分层架构给了清晰的切割面：Inspector 切"Server 对不对"，日志分"哪一层不对"。养成"先隔离再归因"的习惯，链路虽长，排查却有章可循。
