上一篇给了 MCP 的鸟瞰图。这一篇把协议的心智模型钉死：三个角色、三类原语、一次调用的完整时序。这几个概念钉准了，后面读任何 SDK 文档都不会迷路。

## 三种角色

```
┌─────────────────────────────┐
│ Host（宿主应用）              │  Claude Desktop / Cursor / 你的产品
│  ┌──────┐    ┌──────┐       │
│  │Client│    │Client│       │  每个Server一条连接
│  └──┬───┘    └──┬───┘       │
└─────┼───────────┼───────────┘
      │           │
 ┌────▼───┐  ┌────▼────┐
 │Server A│  │Server B │     GitHub / 数据库 / 文件系统…
 └────────┘  └─────────┘
```

- **Host**：用户面对的 AI 应用。它负责管理 LLM 对话、决定何时调用工具、执行安全策略。一个 Host 可以同时连多个 Server。
- **Client**：Host 内部的连接器，与一个 Server 保持 1:1 会话。你通常不直接写它——SDK 和 Host 框架都封装好了。
- **Server**：独立进程，暴露能力（工具/资源/模板）。它可以访问本地资源（文件系统、数据库），也可以代理远程 API。

关键理解：**Server 是"能力提供方"，Host 是"决策方"，模型是"大脑"**。模型看到的是 Host 整理后的工具清单，它说"我要调 X"，Host 通过 Client 找到对应 Server 执行，结果回填进对话。

## 三类原语（Server 暴露什么）

| 原语 | 类比 | 由谁触发 | 典型例子 |
| --- | --- | --- | --- |
| **Tools（工具）** | 可执行的函数 | 模型决定调用 | 查询数据库、发消息、创建文件 |
| **Resources（资源）** | 可读取的文件/数据 | 应用或用户读取 | 日志文件、配置、文档内容 |
| **Prompts（提示模板）** | 预置的技能模板 | 用户主动选择 | "代码评审"模板、"周报生成"模板 |

记忆法：**Tools 是"手脚"（模型自主用），Resources 是"资料库"（按需读），Prompts 是"说明书"（人来点）**。三者都是 Server 的可选项，最常用的是 Tools。

另外两个通用概念：**Sampling（采样）**——Server 反过来请 Host 的模型帮忙完成子任务（如总结抓到的网页）；**Roots**——Host 告诉 Server 可访问的目录边界。初学阶段了解即可。

## 一次工具调用的完整时序

以"用户让 Cursor 查一个 GitHub issue"为例：

1. **初始化**：Host 启动时与每个 Server 握手，交换协议版本与能力声明；
2. **发现**：Host 向各 Server 请求工具清单，得到"github — 提供 search_issues / get_issue 等工具，参数如下…"；
3. **注入**：Host 把所有工具描述（JSON Schema 格式）放进模型的系统上下文；
4. **决策**：模型看到问题，决定"调用 get_issue，参数 issue_id=123"；
5. **执行**：Host 校验请求（权限/参数），经 Client 发给 GitHub Server；Server 执行 API 调用，返回结果；
6. **回填**：结果作为工具返回值进入对话，模型据此生成最终回答。

理解这个时序，你就明白三件事：**工具描述写得好坏直接影响模型会不会用、用得对不对**（第 3 篇）；**Host 的校验环节是安全边界**（第 9 篇）；**延迟=模型决策+网络+执行**（第 8 篇调试）。

## 与 Function Calling 的精确关系

模型侧的"工具调用"能力（Function Calling）负责第 4 步的决策；MCP 负责第 2、3、5 步的标准化——工具如何被统一发现、描述、跨进程执行。两者不是竞争关系：支持 MCP 的应用，最终依然把工具以 function 的形式喂给模型。
