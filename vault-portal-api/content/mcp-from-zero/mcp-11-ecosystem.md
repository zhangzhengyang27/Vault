最后一篇回答一个每天都会遇到的问题："我要接 X，有没有现成的 MCP Server？没有的话自己写要多久？"

## 寻源：三层来源

1. **官方维护**：modelcontextprotocol 组织下的参考实现（GitHub、文件系统、Slack、数据库等），质量与安全基线最高，是"标准实现姿势"的活教材；
2. **厂商官方**：SaaS 厂商为自家产品发布的 MCP Server（或托管端点）——连自家服务，永远先查厂商是否已官方支持；
3. **社区生态**：数以千计的社区 Server 分散在 npm/PyPI 与各聚合目录里（本站 MCP 目录做了中文筛选与整理，可按分类浏览）。质量参差是常态，评估清单见下。

## 评估一个社区 Server 的清单

- [ ] 维护活跃：近几个月有 commit/发版，issue 有回应
- [ ] 来源可信：官方/知名团队，或代码量小到可以通读
- [ ] 权限合理：申请的 token scope 与功能匹配（读功能不该要写权限）
- [ ] 返回与描述一致：用第 8 篇 Inspector 抽查工具行为
- [ ] 供应链干净：依赖少而正常，无混淆代码
- [ ] 安装方式标准：走 npm/PyPI 锁版本，不执行来路不明的 install 脚本

不满足前三条之一，宁可用第 6 篇的方法自己写个薄的。

## 自建判断：三问决策

**问题一：现成的够用吗？** 你的需求若是标准 SaaS 的通用操作（查 issue、发消息），官方/厂商 Server 直接用。别为省两小时写代码引入一个要长期维护的自建件。

**问题二：内部系统还是公共 API？** 公共 API 大概率有人做过（搜聚合目录）；**内部系统必须自建**——而且这正是 MCP 对企业的核心价值：把内部系统一次 MCP 化，所有 AI 工具即插即用（第 10 篇场景三）。

**问题三：薄壳还是业务？** 自建分两档——"薄壳"（几十行，把内部 API 包装成 3-5 个工具，一天内完成）与"业务 Server"（含权限、审计、多租户，按产品需求规划）。绝大多数起步需求是薄壳；薄壳先行，验证价值再演进成业务 Server。

## 一个务实的企业路线图

1. **第 1-2 周**：装官方 Server（文件、GitHub、数据库只读），让团队在现有 AI 工具里尝到甜头，同时收集"最想自动化的三件事"；
2. **第 3-6 周**：为呼声最高的内部系统写薄壳 Server（第 6 篇方法 + 第 10 篇场景三的安全清单），小范围试点；
3. **第 2 个月起**：升级为带 OAuth 与审计的团队服务（第 5 篇形态二），建立 Server 白名单与使用规范（第 9 篇）；
4. **持续**：工具描述的迭代（第 3 篇）按第 8 篇的观测数据驱动——MCP 的运营重点会逐渐从"接更多"变成"接得准、用得安全"。
