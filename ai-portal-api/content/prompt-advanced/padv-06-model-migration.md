你的提示词写得再好，也只是"对某个模型"写得好。模型升级、供应商切换、成本优化换小模型——每一次迁移都是提示词资产的重新校准。这一篇讲迁移的系统方法，让"换模型"从灾难变成一周的常规工程。

## 为什么提示词不是模型无关的

三个差异源：

1. **训练数据与风格**：不同模型对同一指令的"默认理解"不同——"简洁"在 A 模型是三句话、在 B 模型是一句话；中文表达习惯差异更明显；
2. **指令遵循的偏好**：对格式约束、负面指令（"不要…"）、复杂嵌套条件的服从度不同；
3. **能力分布不均**：A 模型代码强、B 模型长文稳——你的提示词若依赖了 A 的某项隐性能力，到 B 就露馅。

**好消息是差异集中在少数维度**，多数提示词（角色、任务、约束、示例）跨模型都基本成立——不稳的通常集中在：输出格式的细节、长链指令的中间步骤、以及依赖模型"隐性知识"的部分。

## 迁移的系统方法

**第一步：分层盘点。** 把现有提示词按"对模型行为的依赖度"分三档：

- 通用层（角色/任务/约束/示例）：预期直接可用；
- 敏感层（输出格式细节、长流程多步指令）：预期要调；
- 依赖层（利用特定模型的隐性能力/特定解析习惯）：预期要重写。

**第二步：评测护航（不可跳过）。** 用现有评测集（第 7 篇）在新模型上跑全量基线——**先知道差多少，再决定动多少**。常见结果：80% 的提示词指标无显著差异，精力集中到真正回退的 20%。

**第三步：逐个修复回退项。** 按第 2-5 篇的方法重调，每修一个跑一次回归。修复方向的经验规律：

- 格式不稳 → 加结构化约束（第 3 篇），少靠"措辞默契"；
- 步骤丢失 → 分解指令、缩短链条（第 2 篇）；
- 风格漂移 → 示例顶上（第 4 篇），示例的迁移性远好于形容词。

**第四步：新旧并行观察。** 灰度切流（第 8 篇），生产指标稳定后再下线旧路径。

## 降低迁移成本的设计习惯

从写提示词的第一天就为未来迁移留余地：

1. **别依赖模型的"默认行为"**：一切你依赖的输出特征都显式写明——"默认值"就是迁移时的隐藏地雷；
2. **输出走结构化接口**（第 3 篇）：约束解码的输出跨模型稳定得多；
3. **示例优于形容词**：示例的可迁移性最高，提示词的"文学性措辞"迁移性最差；
4. **保持评测集与提示词同步版本化**（第 8 篇）：迁移的全部底气来自"随时能测"。

## 一个反直觉的策略

**别追求"一套提示词打天下"。** 为每个主力模型维护一份校准版（差异用变量模板管理，主体共享），比维护一份"四不像通用版"效果好得多。成本可控——通用层占 80% 且共享，敏感层按模型分叉。这就是"多模型矩阵"的维护现实：共享主干 + 每模型一层薄适配。

## 小结

迁移不是重写，是"分层盘点 → 评测护航 → 定点修复 → 灰度切换"的常规工程；日常写提示词时少依赖默认行为、多用结构化与示例，迁移成本就在源头被压低了。下一篇：让每一次修改都敢上线——提示词的回归测试。
