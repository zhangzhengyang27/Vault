测试（第 7 篇）告诉你"能不能上"，这一篇讲"怎么上"：提示词作为资产的存储、参数化、灰度与回滚。这四件事合起来，回答一个关键问题——**半年后，你还能说清"线上这个行为是哪版提示词造成的"吗？**

## 仓库结构：提示词是代码

```
prompts/
  system/
    assistant-zh.md          # 系统提示词
  templates/
    refund-reply.md          # 业务模板(含 {{变量}})
  fewshot/
    refund-examples.json     # 示例库(第4篇)
  evals/
    cases/*.yaml             # 测试用例(第7篇)
  CHANGELOG.md               # 每版改动说明与动机
```

管理规则与传统代码一致：进 git、PR 评审、改动有说明（**为什么改**比改了什么更重要）、发布打 tag。运行时**禁止**从数据库/后台热改提示词——"线上临时改一句"是审计灾难的开始；确需紧急变更，走一次正式的快速发布。

## 参数化：主干与变量分离

同一提示词的大量内容是重复的（角色、规则），变的只是任务段。模板化拆分：

```markdown
{{system_core}}
# 任务
{{task_instruction}}
# 输出要求
{{output_spec}}
```

- **system_core**：全局系统提示词（第 5 篇），低频变更；
- **task_instruction / output_spec**：按任务/场景/语言分叉的变量，高频变更；
- 收益：变更影响面清晰（改任务模板不会波及全局人格）、跨模型适配（第 6 篇）只需分叉敏感层、多语言场景自然支持。

## 灰度与 A/B

提示词的"发布"建议始终走灰度：

1. **分流**：按用户/会话 hash 分桶，5% → 25% → 100%；同一会话粘住同一版本（用户不该在一轮对话里感觉到人格切换）；
2. **看什么**：第 7 篇的断言指标之外，看业务信号（完成率、人工接管率、点踩率）与成本（token 消耗）——A/B 的胜负判据在评测集里定，业务信号里验；
3. **B 版怎么写**：一次只改一个假设（"加了引用要求是否降低点踩"），多变量同改的实验读不出结论；
4. **时长**：覆盖一周内的流量波动周期，样本量按业务峰值预估——别用半天的数据宣布胜负。

工程实现不需要复杂平台：提示词配置带版本号 + 网关按会话 hash 选版本 + 双版本的指标分别打标即可起步。

## 回滚与审计

- **一键回滚**：网关把版本指针切回上一 tag，秒级生效——前提是运行时按版本加载配置（上面仓库结构的直接回报）；
- **审计线**：每条用户请求的日志带上"提示词版本号"（Agent 库第 7 篇的 run 轨迹里加一列）——半年后回答"这个行为是哪版造成的"全靠它；
- **变更窗口**：大版本升级避开业务峰值；紧急回滚不需要窗口，这就是版本化的意义。

## 与团队协作

提示词评审的参与者不止工程师：业务方看规则是否对齐策略、法务看合规表述、测试看用例覆盖。**把提示词的 diff 打印出来贴在评审里**（它就是纯文本），是 AI 团队里门槛最低、收益最高的协作仪式。

## 小结

版本化四件套：git 仓库 + 参数化模板 + 灰度分流 + 一键回滚，外加"日志带版本号"这根审计线。做到这些，提示词系统就从"手工作坊"进入"可运维资产"的行列。下一篇回到内容本身：多模态与工具场景的提示词要点。
