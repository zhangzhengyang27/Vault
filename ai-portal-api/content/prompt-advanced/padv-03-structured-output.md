模型输出给机器用（程序解析、入库、下游调用）时，"大概是个 JSON"是不够的——一个缺引号就能让整个流水线崩掉。结构化输出是把模型的自然语言能力装进工程管道的标准接口，这一篇讲怎么做到"严格可解析"。

## 第一层：Schema 写进提示词的艺术

最朴素的方案是把期望的 JSON 结构写进提示词。写得好坏差别巨大：

1. **给 schema 且给示例**：先贴字段定义，再给一个**填好的完整示例**——模型对模仿示例的忠实度远高于读字段说明；
2. **字段名自解释**：`refund_reason_code` 好过 `code`；枚举值全部列出并解释语义；
3. **说明"不要什么"**："不要输出 JSON 以外的任何字符，不要用 markdown 代码块包裹"——自由发挥的主要来源就是这些边角；
4. **处理空值**：定义"信息缺失时该字段填 null 还是省略"——不定义，模型每次的选择都可能不同；
5. **字段数量克制**：一次要 20 个字段的抽取，准确率一定低于拆两次各 10 个。

## 第二层：约束解码与 JSON 模式

提示词是软约束，**约束解码（constrained decoding）是硬约束**：推理引擎在生成时就限制每个 token 必须符合 schema——语法层面不可能产出非法 JSON。

- 各家 API 的"JSON 模式 / Structured Outputs"（传 schema，输出保证合法）已是主流能力，**优先用它**，提示词里就只需管语义质量；
- 本地部署同样支持：vLLM 等引擎提供 guided decoding（本站本地部署库第 6 篇的服务能力之一）；
- 注意硬约束管语法不管语义：字段合法但内容张冠李戴的问题依然存在，语义质量仍靠提示词与校验。

## 第三层：校验-修复循环

无论如何，生产系统要假设"会有不合法输出"，最后一道防线是程序化校验+修复：

```
输出 → Pydantic/schema 校验 → 通过? 使用
                              ↓ 失败
                     修复调用："你的输出有如下错误:[...]
                              原始输出:[...]，只返回修正后的JSON"
                              ↓ 仍失败(重试1-2次)
                     降级：人工队列/默认值/报错
```

要点：修复调用把**校验器的具体错误**喂回去（"age 字段期望 integer，收到 '二十'"）——模型按错误自愈的能力很强（Agent 库第 3 篇的同款原理）；修复限次，2 次不过走降级，别无限循环烧钱。

## 该不该上结构化：一个判定方法

结构化有真实代价：字段约束会压缩模型的表达自由度，开放性任务（写文案、头脑风暴）强行 JSON 化是自缚手脚。判定三问：

1. 下游是**程序**消费输出吗？是 → 必须结构化；
2. 输出字段是**封闭集合**（分类/抽取/判断）吗？是 → 结构化收益最大；
3. 输出是**开放生成**吗？是 → 保持自然语言，把"结构"留给后处理。

半开放任务（"生成带标签的要点列表"）的中间态做法：约定轻量格式（Markdown 标题+固定前缀）+ 宽松解析，比硬 JSON 更不伤质量。

## 抽取类任务的进阶技巧

结构化输出最常用于信息抽取，三个提准技巧：

- **少样本覆盖边界**（第 4 篇展开）：示例里必须包含"字段缺失"和"歧义"的例子；
- **先引用后判断**：要求模型先摘录原文依据（span），再做字段判断——依据与结论绑定，幻觉率明显下降（RAG 库第 8 篇引用思想在抽取任务的应用）；
- **分而治之**：长文档抽取按章节切片分别抽取后合并去重，比整篇抽一次更稳。

## 小结

结构化输出三层防线：schema 提示词（语义）→ 约束解码（语法）→ 校验修复循环（兜底）；开放任务别硬上 JSON。下一篇：把"给示例"这门手艺讲透——少样本示例工程。
