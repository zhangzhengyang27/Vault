"我改了一句提示词，好像更好了？"——没有测试，这句话永远无法被证实或证伪。提示词测试是把前几篇的技术（推理、结构化、示例）安全组合起来的保险丝，也是整个提示词工程体系的承重墙。

## 测试用例的四类断言

一个提示词测试用例 = 输入 + 断言。断言分四类，从便宜到贵：

| 断言类型 | 检查什么 | 实现成本 |
| --- | --- | --- |
| **结构断言** | 输出可解析、字段齐全、枚举合法 | 纯代码，零成本 |
| **内容断言** | 关键要素在/不在（含某结论、不含某禁词、提到某来源） | 代码+关键词表 |
| **语义断言** | 与参考答案的相似度、要点覆盖 | 嵌入相似度/LLM-as-judge |
| **评分断言** | rubric 分数 ≥ 阈值 | LLM-as-judge 校准（Agent 库第 6 篇方法） |

设计原则：**能用便宜断言就不用贵的**。结构断言能拦住的问题不要留给 judge；每类用例选 1-2 个主断言，全套断言会拖慢速度与稳定性。

## 评测集的构建

与 RAG 库第 9 篇同源的方法，提示词场景的三个特别提醒：

1. **用例覆盖"修正历史"**：每个曾出过的 bad case 都变成一条测试用例——你的测试集就是系统的病历本；
2. **覆盖任务分支**：正常/边界/无答案/对抗输入（注入试探、越权请求）各占一档——**对抗用例是安全回归的地基**（Agent 库第 9 篇）；
3. **规模务实**：核心提示词 30-100 条用例足够支撑日常回归；judged 用例控制占比（贵且慢），日常跑结构+内容断言全量、语义断言抽样。

## 三种测试场景

1. **改前基线**：动手改提示词前，先跑一遍记录基线——"好像更好"必须有数字对照；
2. **改后回归**：改动跑全量测试集，重点看：目标用例是否改善、**其他用例是否被殃及**（提示词的改动的杀伤半径常常超出预期）；
3. **周期性全量**：模型供应商升级、换了部署环境、每周期固定跑——捕捉"你没改任何东西但它变了"的环境漂移。

## CI 里的提示词门禁

提示词进版本管理（第 8 篇）后，测试接入发布流程：

```
修改提示词 → PR → 自动跑测试集(结构断言全量+语义断言抽样)
  → 核心断言不通过 = 阻断合并
  → 语义指标回退超阈值 = 需要人工评审标注原因
  → 通过 = 合并 → 灰度发布
```

两个工程注意：judge 调用有成本与抖动，测试环境锁定模型版本与温度（0），多次采样取稳定结论；测试失败的输出要**存档展示**——评审者要能看到模型实际说了什么，而不是只看一个分数。

## 从测试到运营

- **测试集是资产**：与提示词同版本管理，每个用例标注"来历"（哪个 bug/哪个需求）；
- **失败即素材**：线上 bad case（用户点踩、纠错）进入测试集的速度，决定系统自我修复的速度；
- **指标趋势**：按周记录核心用例的通过率曲线——缓慢下滑往往是模型漂移的第一个信号（第 6 篇环境漂移的哨兵）。

## 小结

提示词测试 = 四类断言（便宜优先）+ 病历本式评测集 + 改前基线/改后回归/周期全量 + CI 门禁。它的回报是心理层面的：**敢改**。下一篇讲版本管理与灰度——测试之外，发布侧的另一半工程。
