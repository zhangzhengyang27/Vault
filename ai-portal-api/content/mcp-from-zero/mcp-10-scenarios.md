概念、实现、调试、安全都齐了。这一篇用三个最常见的企业场景，把前面所有内容串成可落地的方案——每个场景都按"工具清单 + 安全边界 + 常见坑"展开。

## 场景一：只读数据库助手

**需求**：让产品和运营直接用自然语言查数，不用排队找数据分析师。

**工具设计（刻意保持小）**：

```
list_tables()                  → 列出可查的表与字段说明
sample_rows(table, limit)      → 抽样几行看数据长什么样
query(sql)                     → 执行只读 SQL，返回截断的结果集
```

**关键设计决策**：

1. **只读账号 + 库级隔离**：Server 用一个只能 SELECT 的数据库账号连接——这是整个方案的安全根基，比任何提示词约束都硬；
2. **自动加 LIMIT 与超时**：查询层强制 `LIMIT n`（如 200）与执行超时，防止全表扫描打挂库；
3. **schema 即文档**：`list_tables` 的返回里给每个字段写清含义与枚举值（第 3 篇：描述就是提示词）——模型写对 SQL 的准确率主要取决于此；
4. **结果截断要声明**："共 3400 行，已返回前 200 行"（第 3 篇分页原则）。

**常见坑**：让模型"自由发挥"写复杂 JOIN 不可靠——把高频查询固化成 `query_top_customers(period)` 这类业务粒度工具（第 3 篇粒度上移），SQL 只兜长尾。

## 场景二：受控浏览器自动化

**需求**：让 Agent 查内网系统、填表、截图——浏览器是最通用的"人机接口"。

**工具设计**：

```
navigate(url) → 打开页面并返回可访问性树/元素快照
click(ref) / fill(ref, text) → 按快照里的元素引用操作
screenshot() → 截图返回
```

**关键设计决策**：

1. **操作对象用元素引用（ref）而不是裸坐标**——引用来自上一轮快照，稳定且可审计；
2. **域名白名单**：Server 侧限制可访问的域名集合，这是防提示注入借浏览器外泄数据的硬边界（第 9 篇）；
3. **登录态隔离**：用独立的浏览器 profile，只登录必要站点，绝不复用个人日常 profile；
4. **每一步快照即审计日志**：做了什么操作，全部留痕。

**常见坑**：页面是"活的"（弹窗、异步加载），工具返回里要把"当前页面状态"描述清楚，否则模型的下一步操作就是盲操。

## 场景三：内部系统 MCP 化

**需求**：把公司自研的工单/CRM/审批系统接进所有 AI 工具——MCP 在企业里最典型的价值场景。

**落地路径（推荐顺序）**：

1. **先做查询类工具**（`list_my_tickets()`、`search_customer(keyword)`）——低风险，快速建立信任；
2. **再加事务类工具**（`update_ticket_status(id, status)`）——此时第 9 篇的完整安全体系必须到位：按用户身份的 OAuth token（服务端"替用户"调用，权限=用户本人在系统里的权限）、写操作人机确认、全量审计日志；
3. **配一条 Prompt 原语**：把"怎么查工单、怎么判断优先级"的团队流程做成 `/triage` 模板（第 4 篇），工作流产品化。

**常见坑**：内部接口文档缺失导致工具描述含糊——宁可花一天整理字段含义，也别让模型对着 `upd_st(x, y)` 猜。权限放大是最常见事故源：一个持全局 API key 的 Server 意味着任何接入的 AI 都能看到全公司数据（第 9 篇混淆代理）。

## 三个场景的通用模式

回看会发现一套重复出现的骨架：

- **只读先行，写操作后置且强管控**；
- **业务粒度工具 + 少量兜底原子工具**；
- **硬边界（账号权限/白名单/隔离）优于软约束（提示词）**；
- **每步留痕，审计即日志**。

按这个骨架，你可以把任何"让 AI 接入 XX 系统"的需求拆成一份安全的实施清单。下一篇收官：生态地图——先找现成的，还是自己造。
