Tools 是 MCP 最核心的原语——绝大多数 Server 的价值都在这里。但"暴露一个函数"和"设计一个好用的工具"是两回事：模型是根据**工具的名字、描述和参数 schema** 来决定用不用、怎么用的。这一篇讲把工具设计到"模型一次调对"的要点。

## 描述就是提示词

模型选择工具时看到的是：

```json
{
  "name": "search_issues",
  "description": "在 GitHub 仓库中搜索 issue。返回匹配的 issue 列表（含标题、编号、状态）。用自然语言关键词搜索；按编号查单个 issue 请用 get_issue。",
  "inputSchema": { ... }
}
```

三个设计要点：

1. **描述写"何时用 + 何时不该用 + 返回什么"**，而不只是"是什么"。"用自然语言搜索；按编号查询请用 get_issue"这句话避免了最常见的混淆调用。
2. **名字用动词短语**：`search_issues` 优于 `github_data`。相近工具名要有区分度（search / get / list / create / update），让模型望文知义。
3. **工具要少而精**：20 个职责模糊的工具不如 5 个边界清晰的。工具越多，模型选错的概率越高、上下文开销越大。

## 参数设计的最佳实践

- **参数数量克制**：必需参数越少越好；可选参数给足默认值。模型填错参数的误差随参数个数上升。
- **每个参数写清说明**：单位、格式、取值范围。"date（字符串，ISO 8601 格式，如 2026-09-14）"远好于"date（日期）"。
- **枚举代替自由文本**：能收窄成 enum 的参数就收窄（`status: "open" | "closed" | "all"`），模型选枚举的准确率远高于自由发挥。
- **危险参数显式标注**：删除、覆盖、发送类操作的参数描述里写明后果，给 Host 侧的确认逻辑留出抓手。

## 返回值与错误：给下一轮模型看的信息

工具的返回会作为上下文喂回模型继续推理，所以要为"被模型阅读"优化：

- **结构化 + 自解释**：返回 JSON 时带上字段含义，或返回渲染后的文本；纯 ID 列表不如带标题/状态的摘要列表。
- **分页与截断要声明**：结果被截断时明确说"共 245 条，已返回前 20 条，可用 offset 参数获取更多"——模型才知道需要翻页。
- **错误信息可恢复**：不返回裸堆栈，返回"发生了什么 + 模型该怎么做"：`"日期格式错误，请使用 YYYY-MM-DD 格式重试"`。**好的错误信息是一次自愈机会**，差的错误信息直接终结对话。
- **别返回敏感数据**：返回值会进上下文（意味着可能进日志），密钥、全量个人数据不应出现在工具返回里——这也是第 9 篇安全设计的一环。

## 粒度：高内聚的工具组合

把"业务动作"设计成工具，而不是把"原子 API"堆成工具集：

- ✗ `read_file` + `write_file` + 自己拼"读取模板→改内容→写回"
- ✓ `create_report_from_template(template_id, data)`

模型多步编排的每一步都是出错机会。粒度上移一层，把多步原子操作封装成一个"可靠动作"，调用准确率显著提升——这与提示词工程里"任务粒度"的直觉一致。

## 小结

工具设计 = 描述工程 + 参数约束 + 模型友好的返回值 + 业务粒度封装。写完工具，用真实的模糊问句测一轮："帮我看看上周那个 issue 怎么样了"——模型能选对工具、填对参数，才算设计完成。
