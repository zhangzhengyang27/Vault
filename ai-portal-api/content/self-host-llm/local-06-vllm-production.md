vLLM 是自建推理服务的事实标准（第 4 篇）。这一篇给出从裸机到"可交付给团队使用"的完整步骤，以及三个最关键的调优维度。

## 安装与启动

推荐容器化（环境隔离、升级干净）：

```bash
docker run --gpus all -v ~/.cache/huggingface:/root/.cache/huggingface \
  -p 8000:8000 vllm/vllm-openai:latest \
  --model Qwen/Qwen3-14B-Instruct \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.90
```

服务起来后就是一个 **OpenAI 兼容 API**（`http://<host>:8000/v1`）——第 5 篇的应用代码一行不用改，把 base_url 指过来即可。

## 启动参数：五个最关键的两个

1. `--max-model-len`：最大上下文长度。**它决定 KV 缓存上限**，设得越大并发容量越小。按真实业务需要设（对话 8-16k 够用），别开满模型上限。
2. `--gpu-memory-utilization`：vLLM 可用的显存比例（默认 0.9）。预留太少浪费，太多会 OOM——单卡专用场景 0.9 起步。

其余常用：`--quantization`（量化方案，第 7 篇）、`--tensor-parallel-size`（多卡切分）、`--served-model-name`（对外暴露的模型名）。

## 调优三维度

**1. 吞吐与并发的平衡。** vLLM 的 continuous batching 会自动把并发请求拼批处理。看服务健康度的核心指标是 `num_requests_waiting`（排队数）与单 token 延迟：排队持续增长 = 容量不足，需要降 max-model-len、量化换更小的模型或加卡。

**2. 长上下文 vs 高并发的取舍。** 这两者在同一张卡上此消彼长（KV 缓存），没有免费午餐。方案：按业务拆实例——长文档处理单独一个实例（低并发、大 len），高并发问答一个实例（小 len）；比一个大而全实例更稳。

**3. 前缀缓存的红利。** 相同系统提示词/长前缀的请求可复用 KV 缓存（vLLM 自动开启 prefix caching）——把系统提示词设计成统一前缀（第 10 篇上下文工程的缓存红利），多轮与高频场景吞吐提升显著。

## 服务化必备件

vLLM 只管推理，生产服务还需要外面一圈（第 8 篇展开运维细节，这里给最小清单）：

- **网关**：加一层 Nginx/Caddy 做鉴权（vLLM 自身无鉴权）、限流、HTTPS；
- **健康检查**：`/health` 端点接入探活；监控 token 吞吐、排队数、显存占用；
- **日志与计费**：记录每次调用的模型、token 数、耗时——第 11 篇成本核算的数据底座；
- **模型版本锁定**：`--model` 用明确版本 tag（不要 latest），升级按发布流程走（第 12 篇 Agent 库的发布纪律同构）。

## 容量规划速算

1. 目标并发 C 与平均上下文长度 L（输入+输出）；
2. KV 缓存需求 ≈ C × L × 每token缓存系数（与模型层数/头数相关，引擎会自己分配，你只需留出空间）；
3. 实测校准：以真实流量回放压测，观察排队与延迟曲线，得出"这张卡/这个配置"的实际安全并发数——**配置表算出的只是起点，压测数据才是结论**。

## 常见故障速查

| 症状 | 方向 |
| --- | --- |
| 启动即 OOM | max-model-len 或 gpu-memory-utilization 过大；换量化版 |
| 跑一阵 OOM | 并发峰值 KV 缓存超限；限流或缩 len |
| 吞吐远低于预期 | 检查是否意外走了 CPU；序列化瓶颈；长度设置不当 |
| 偶发超时 | 排队堆积；加并发预算告警（第 8 篇） |
