"我们微调一个自己的模型吧"——很多项目的失败从这句话开始。微调（Fine-tuning）是本库最贵的工具，用对场景价值巨大，用错场景是纯粹的浪费。这一篇先立决策框架，后面两篇再讲实操。

## 先做排除法：多数需求不需要微调

拿你的需求对照三分框架：

| 需求本质 | 正确工具 | 为什么不是微调 |
| --- | --- | --- |
| 模型不知道**新知识/私有知识** | RAG | 微调把知识"压"进参数，更新要重训、无法溯源、还可能学错——知识问题 RAG 全面占优（本站 RAG 库第 1 篇的对照表） |
| 行为不对但**例子能说清** | 提示词/少样本 | 几个好例子放提示词里，效果常胜过几百条训练数据，且随改随生效 |
| 输出要**稳定的格式/风格/流程** | 提示词 → 微调 | 先把格式要求写进提示词试；提示词已经臃肿到失控、或每 token 都在为格式花钱时，微调才划算 |

**微调真正不可替代的场景**：

1. **风格与语言习惯的深度内化**：让模型稳定模仿一种文风、行业表达方式、角色人格——不是靠提示词"演"，而是真的会；
2. **结构化任务的格式可靠性**：让模型在高并发下稳定输出严格 schema（提示词约束 + 输出修复循环也能做，微调更省心省 token）；
3. **领域术语与判断逻辑**：法律/医疗/内部的行话体系与判断模式，示例驱动学得快忘得慢；
4. **小模型替代大模型**：把旗舰模型的"处理特定任务的能力"蒸馏到小模型上——省钱的正统路线（成本从每 token 变成一次性）；
5. **指令遵循的极致优化**：任务很窄很固定（分类、抽取、改写），微调后小模型又快又准。

## 微调的真实门槛

在决定微调前，确认这三件事都能满足：

1. **数据**：几百到几千条**高质量**样本（质量远比数量重要——500 条精心造的数据胜过 5 万条脏数据）。数据从哪来：人工标注、生产日志清洗、强模型蒸馏生成（用旗舰模型生成示例再人工校对）；
2. **评估**：一套能量化"微调后更好了"的评测集（RAG 库第 9 篇方法）——没有评估的微调无法验收，等于闭眼开枪；
3. **迭代能力**：微调不是一次性的——数据要随 bad case 持续补充，训练要可重复（配置进版本管理）。

三者缺一，先把缺的补上再回来。

## 微调的形态谱系

从轻到重（第 10 篇实操前两档）：

- **提示词/上下文学习**：零训练，随改随生效；
- **LoRA/QLoRA**（主流）：不动原模型权重，只训练一小片"插件"（几 MB 到几百 MB），单卡可训，可插拔组合——**90% 的微调需求停在这一档**；
- **全参微调**：重训全部权重，效果上限最高，需要多卡训练资源与更多数据——只有前两档确实到顶才考虑；
- **预训练/继续预训练**：另一个世界，业务团队几乎不会触碰。

## 一个决策案例

"客服机器人回答总用英文腔、抓不住我们产品名"——拆开：产品名抓不住是**知识问题**→RAG；英文腔是**风格问题**→先试提示词给范例；两种手段调完仍不稳定、且日调用量大 → 用生产日志清洗出几千条优质客服对话，LoRA 微调 8B 模型——既解决风格又把服务从旗舰 API 搬到本地（省钱闭环）。**顺序永远是：RAG/提示词在前，微调收尾。**
