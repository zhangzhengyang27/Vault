模型选好了，用什么跑？推理工具不是越强越好，而是分工不同。这一篇按使用阶段给一张分工地图，以及它们之间的迁移路径（好消息：模型格式基本通用，换引擎不用换模型）。

## 分工地图

| 工具 | 定位 | 适合谁 | 一句话点评 |
| --- | --- | --- | --- |
| **Ollama** | 桌面级一键运行 | 个人、演示、原型 | `ollama run qwen3` 一条命令跑起来，自动管理模型下载与量化；本地 API 即 OpenAI 兼容。牺牲吞吐换易用 |
| **llama.cpp** | 极客底座 | 想抠细节、跑在 CPU/Mac/边端 | 几乎所有量化格式的发源地（GGUF），CPU 推理与苹果芯片优化最好；Ollama 底层也在用它 |
| **vLLM** | 生产吞吐标配 | 团队/企业服务 | PagedAttention 高效管理 KV 缓存，continuous batching 高并发吞吐强，OpenAI 兼容服务开箱即用——**自建服务的默认选择** |
| **SGLang** | 高阶批处理 | 复杂调度/超大吞吐 | RadixAttention 前缀缓存等优化突出，结构化/多轮场景性能强；社区活跃度与文档略逊 vLLM |

另有 NVIDIA 系的商业方案（TensorRT-LLM 等）追求极限吞吐，配置复杂，企业级再考虑；各家云厂商的"一键部署"服务本质是帮你托管上面这些引擎。

## 按阶段的演进路径

**阶段一：验证（Ollama）。** 个人电脑 `ollama pull` + `run`，十分钟确认"这个模型对我的任务够不够好"（第 5 篇全流程）。这一步不要碰 vLLM——你在验证模型，不是在生产。

**阶段二：小规模服务（Ollama 或单卡 vLLM）。** 团队十来人轻度使用，Ollama 挂内网也能顶；并发上来后切 vLLM。

**阶段三：生产服务（vLLM/SGLang）。** 稳定并发、需要监控与弹性——上 vLLM（第 6 篇全流程），极端吞吐或复杂调度再对比 SGLang。

**跨阶段不变的**：模型与量化格式（GGUF 通用性最好；vLLM 常用 AWQ/GPTQ/safetensors）、OpenAI 兼容 API 层（应用代码不用改）、评测集（换引擎后回归一遍即可）。

## 选引擎时真正要看的四个参数

无论哪个引擎，评估时盯这四个：

1. **吞吐（tokens/s，按并发数）**：服务能力的核心指标，用你真实的上下文长度测，别信厂商的理想值；
2. **KV 缓存管理**：长上下文 + 高并发下的显存效率（vLLM 的强项所在）；
3. **量化格式支持**：你选的模型有没有现成的对应格式版本；
4. **OpenAI 兼容度**：流式、function calling、多模态接口是否完整——决定你应用层改多少。

## 两个常见弯路

1. **过早优化**：验证阶段就上多卡 vLLM 集群调参——先用 Ollama 确认模型行不行，模型不行引擎再强也白搭；
2. **一直留在舒适区**：团队服务还挂在个人版 Ollama 上，并发一高就"模型变笨"（实为排队超时与上下文管理粗糙）——该切 vLLM 就切，迁移成本远低于想象的低。

## 小结

个人验证用 Ollama，抠细节/边端看 llama.cpp，生产服务上 vLLM，追求极致对比 SGLang。模型格式与 API 层保持通用，引擎可随时换。下一篇从最快的路径开始：Ollama 十分钟跑通第一个模型。
