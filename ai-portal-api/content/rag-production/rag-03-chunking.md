把文档切成 chunk（片段）是 RAG 特有的环节，也是新手最容易随手为之的一步。切得好坏直接决定检索命中率：切得对，答案段落完整入索引；切得错，答案被腰斩在两个 chunk 之间，永远检索不到完整证据。

## 为什么"随手切"会出事

最常见的默认做法是按固定 token 数切（比如每 500 token 一块）。它的问题：

1. **语义腰斩**：一个完整的论述被从中间切开，两半单独看都不完整。检索命中了"半句话"，模型拿到的是残缺证据。
2. **上下文孤立**："它比上一代提升了 30%"——"它"是谁？指代被切走后，这段话变得不可解释。
3. **大小一刀切**：目录、表格、正文的信息密度天差地别，统一 500 token 对表格太碎、对论述太粗。

## 实践中的分层策略

**第一优先：按文档结构切。** 解析阶段保留了标题层级（第 2 篇），就按"标题-子标题"边界切，chunk 天然语义完整。规则示例：以最小标题为单位成块；单块过长（超过目标 token 上限）再内部细分；过短的相邻块合并。

**第二优先：重叠窗口兜底。** 对没有结构的纯文本，用固定窗口 + 10-20% 重叠，保证边界信息在两个 chunk 中至少完整出现一次。

**表格整体成块**，绝不从中间切开；必要时把表格转成描述性文本（"该表列出三款产品的价格与内存"）辅助检索。

**元数据随行**：每个 chunk 记录来源文档、章节路径、页码、日期——后续过滤、溯源、去重全靠它。

## 大小怎么定：别抄经验值，做实验

"256 还是 512 还是 1024 token"没有普适答案，它取决于你的文档密度和问题类型。可行的方法：

1. 抽 30-50 个真实用户问题 + 人工标注的正确出处段落，做**评测集**（第 9 篇会展开）；
2. 2-3 种切法各建一版索引；
3. 跑检索命中率（正确出处是否进 Top-K），选赢的。

一般规律可供起点：事实查找类问答偏小块（精度高），论述总结类偏大块（上下文足）；起始值取 300-800 token 区间试。

## 进阶：小-大检索（父子块）

一个漂亮的两全法：**检索用小块（准），生成用大块（全）**。

- 索引时给每个大块（如整节）细分成小子块，向量库里只放小子块；
- 命中小块后，回表取出它所属的大块（甚至整节）交给模型。

这样检索精度由小块保证，上下文完整性由父块兜底。它是"父子块""small-to-big""句子窗口检索"等一批技术的共同思想，也是低成本提升回答质量的第一招。

## 小结

- 结构优先、重叠兜底、表格整体、元数据随行；
- chunk 大小用评测集实验定，不拍脑袋；
- 效果不够时，先试小-大检索，再考虑更复杂的方案。
