到目前为止我们的 RAG 是一条**固定管道**：不管什么问题，都走"检索→重排→生成"。但真实世界的问题不均匀——"公司年假几天"一步检索就够，"对比三款产品的售后政策"需要四次检索加汇总。**Agentic RAG** 把"怎么检索"的决策权交给 Agent：它看着问题，决定查什么、查几轮、用哪个工具。

## Agent 给检索带来的四种能力

1. **路由**：先判断问题类型再选路径。闲聊不走检索、精确事实走 BM25 优先、复杂汇总走多查询分解、"不知道答案在哪"先查目录再定位。固定管道对所有人都走全流程，Agent 按需分配——省钱、省延迟、还减少无关检索引入的噪音。

2. **迭代检索**：第一轮没找到就改写关键词再来，直到找到或确认找不到。朴素管道一轮定生死；Agent 可以"查 A 术语→发现文档里叫 B→用 B 再查"。多跳问题（"A 的供应商的母公司是谁"）靠迭代逐跳逼近。

3. **多源调度**：不只一个检索库——内部 wiki、数据库（SQL 工具）、网页搜索、专用的 GraphRAG（第 11 篇），Agent 按问题性质选源、交叉验证。这是"企业级问答"的自然演进形态。

4. **自检与反思**：拿到检索结果先评估"这些材料够回答吗"，不够就补充检索；回答前再自检"每个论断有证据吗"。把第 8 篇的拒答从"阈值触发"升级为"主动判断"。

## 代价清单

- **延迟**：多轮 LLM 调用（路由、反思、迭代），从"一秒出答案"变"数秒到数十秒"；
- **成本**：同样的 token 消耗乘上轮数；
- **可控性**：Agent 可能"想太多"（过度检索）或"想偏"（错误路由），行为不如固定管道可预测；
- **评估更难**：除了答对率，还要评估"过程合理性"——评测集要加过程标注。

## 实现要点

1. **工具接口干净**：给 Agent 的检索工具返回结构化结果（chunk、来源、分数）+ 清晰的工具描述（第 3 篇的 tools 设计原则同样适用）；
2. **轮数上限 + 超时**：强制封顶（如 3 轮检索），防止失控循环；
3. **观察轨迹**：必须记录 Agent 每步"想了什么、调了什么、为什么"——调试 Agent 检索=看轨迹（本站 Agent 知识库有可观测性专篇）；
4. **混合架构务实**：简单问题走固定管道（快而便宜），复杂问题升级到 Agentic 路径——路由本身就是 Agent 的第一个用武之地。

## 与第 11 篇的关系

GraphRAG 和 Agentic RAG 不冲突，常常组合：Agent 路由后，判断这个问题是"局部事实"（走向量检索）还是"全局汇总"（调图谱摘要工具）。检索策略的组合拳，本质都是同一个思想：**把"对什么都用同一招"升级为"看菜下饭"**。
