RAG 的最终质量上限，在解析这一步就决定了大半。模型只能看到你喂给它的文本——PDF 里丢了表格，问答就永远答不出表格里的数字。这一篇按文档类型给坑位地图。

## 五类高频问题

**1. 扫描件与图片型 PDF。** 没有文本层，直接抽取得到空字符串。必须先 OCR（光学字符识别），再拼回文本。识别质量决定一切，手写体、低分辨率是重灾区。信号：复制 PDF 文字粘贴出来是空的，就是它。

**2. 表格。** PDF 的表格本质上是一堆散落的文字坐标，朴素抽取会得到"列名、数据、再列名"交错的碎片。表格又是企业文档里信息密度最高的部分（报价单、财务表、规格参数）。对策：用带表格结构识别的解析器，把表格转成 Markdown 或 HTML 保留行列关系；关键表格考虑单独抽取、甚至人工校对。

**3. 多栏与复杂版式。** 双栏论文朴素抽取会左右栏交叉混排，语义完全破坏。对策：选支持版面分析的解析器（按阅读顺序重组）。

**4. 层级结构丢失。** 标题、列表、页眉页脚、脚注混成一锅粥后，"这篇文档分几部分"的信息消失，直接影响下一阶段的分块质量。对策：解析时保留 Markdown 标题层级，分块时按结构切。

**5. 重复噪音。** 页眉页脚、水印、目录、免责声明会在每个 chunk 里重复，检索时制造大量假命中。预处理阶段就该剪掉。

## 工具选型速查

| 场景 | 顺手的工具/路线 | 备注 |
| --- | --- | --- |
| 纯文本型 PDF | pdfplumber、PyMuPDF | 快且免费 |
| 复杂版式/表格 PDF | 版面分析类解析服务或模型（各家文档智能产品） | 成本换质量 |
| 扫描件 | OCR 引擎（如 Tesseract 起步，商业 OCR 提质） | 人工抽检 5% |
| 网页 | Readability 类正文抽取 + HTML 转 Markdown | 剥掉导航与广告 |
| Office 文档 | 转 Markdown（保留标题/表格） | docx 比 pdf 友好得多 |
| 多媒体 | 图片走视觉模型打标、音频转写 | 元数据入库 |

一个务实建议：**解析服务的质量差异巨大且随模型进化很快**，选型前拿你们最刁钻的 20 份真实文档跑盲测，比看任何宣传页都准。

## 预处理检查清单

解析之后、切分之前，过一遍：

- [ ] 乱码与编码问题清零
- [ ] 页眉页脚/水印/目录剔除
- [ ] 标题层级保留（Markdown 化）
- [ ] 表格结构化（行列关系完整）
- [ ] 超链接与引用脚注按需保留（出处溯源会用到）
- [ ] 每份文档带元数据：来源、日期、作者、密级——检索过滤（第 13 篇权限）全靠它

## 一条经验

为每种文档类型建立"金标准样本集"（人工确认正确解析结果的 10-20 份），每次改解析配置就回归一遍。解析是 RAG 里最不值得"目测没问题"的环节——它的问题会在几个月后的某次奇怪检索失败里爆出来，那时排查成本高得多。
