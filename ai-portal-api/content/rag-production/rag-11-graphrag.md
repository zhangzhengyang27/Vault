把文档切块进向量库的朴素 RAG，有个结构性盲区：它只见"局部段落"，不见"全局结构"。问"这份年报里公司面临哪三大风险，彼此怎么关联"——答案散在 30 个 chunk 里，Top-K 根本装不下。GraphRAG 用图结构补这个盲区。

## 两类问题的分野

| 问题类型 | 例子 | 朴素 RAG | GraphRAG |
| --- | --- | --- | --- |
| 局部事实 | "X 条款的违约金是多少" | 擅长 | 无必要 |
| 全局汇总 | "全部文档的主要主题有哪些" | 弱（Top-K 视野） | 强（图谱摘要） |
| 多跳关联 | "A 公司和 C 项目通过谁关联" | 弱（中间环节可能不在 Top-K） | 强（沿边遍历） |
| 关系推理 | "哪些供应商同时依赖 X 渠道" | 弱 | 强（关系查询） |

## 两种形态

**形态一：图增强检索（轻量，先试这个）。** 在现有 RAG 上加"图信号"：

- 实体链接：从查询里抽出实体（人名/产品/条款号），优先检索这些实体的相关 chunk；
- 邻居扩展：命中的 chunk 沿文档结构（同章节）或实体关系把"邻居"一并取出；
- 知识图谱当字典用：查实体卡（A 是谁、和谁有关系），辅助查询改写。

成本接近朴素 RAG，适合作为第一步。

**形态二：图谱摘要 RAG（重方案）。** 微软 GraphRAG 方案的代表路线：

1. 用 LLM 从全量文档抽取实体与关系，构建知识图谱；
2. 用社区发现算法把图聚成主题社区；
3. 让 LLM 为每个社区生成"社区摘要"；
4. 全局性问题不再检索 chunk，而是**检索/遍历社区摘要**——视野从"几十个片段"变成"整个知识领域的地图"。

代价直白：建图要 LLM 过一遍全量语料（成本与库容成正比，通常是朴素索引的几倍到几十倍），图质量依赖抽取质量，语料更新要维护增量建图。

## 适用判断

上 GraphRAG 前问三个问题：

1. 你的问题里**全局汇总与多跳关联**占比高吗？（高→值得；都是局部事实→不值得）
2. 语料里实体与关系密集吗？（合同、组织架构、产品线、人物事件→是；散文式内容→否）
3. 朴素管道+重排（第 5-7 篇）真的到顶了吗？（先做完基础优化再谈重方案）

## 小结

GraphRAG 不是朴素 RAG 的替代，是补集：局部事实继续走向量，全局与关系问题走图。多数团队的正确顺序是：评测集 → 基础管道优化 → 发现"全局/多跳类"问题的命中率天花板 → 再引图。下一篇讲另一个进阶方向：让 Agent 接管检索决策。
