RAG 的每个环节都可以"优化"，但没有评估，你无法知道任何一次改动是变好还是变坏。这一篇是全库最重要的一篇：**先建评测，再做优化**，顺序不能反。

## 分层评估：把问题归位

端到端"答案好不好"是个模糊信号，质量必须拆到层：

| 层 | 核心问题 | 指标 |
| --- | --- | --- |
| 检索 | 正确的证据找到了吗 | 命中率、MRR、召回@K |
| 重排 | 好证据排前面了吗 | nDCG、Top-3 命中 |
| 生成 | 证据用对了吗 | 忠实度、答案相关性、引用正确率 |
| 端到端 | 用户满意吗 | 人工评分、用户反馈率 |

分层的好处：检索命中率不涨，说明检索侧改动无效；检索涨了答案没变好，问题在生成侧。**归因清楚，优化才不浪费。**

## 评测集怎么建

评测集是几十到几百条"问题 + 标准出处（gold chunk）+ 参考答案"的三元组。冷启动方法：

1. **真实问题优先**：从用户搜索词、客服记录、同事提问里收集——真实分布比想象重要。
2. **合成补全**：拿语料里的段落让模型反向出题（"根据这段话出 3 个用户会问的问题"），快速铺量；注意合成问题往往"太好答"，要混入真实难度。
3. **难度分层**：简单（答案在某一段内）、多跳（要综合两处）、无答案（库里没有，考验拒答）三类都要有——**无答案样本最常被漏掉，而拒答恰恰是生产底线**。
4. **规模**：50 条能起步，200-300 条能支撑组件选型对比；随 bad case 运营持续扩充。

## 指标怎么算：RAGAS 风格拆解

开源评估框架（RAGAS、TruLens、DeepEval 等）把生成侧指标拆成可计算的维度，核心思想是"用 LLM 当裁判（LLM-as-judge）"：

- **忠实度（Faithfulness）**：答案中的每个论断能否被检索到的证据支持？让裁判模型逐句核对——抓"自由发挥"。
- **答案相关性**：答案是否切题、信息量是否够——抓"答非所问"。
- **上下文精确率/召回率**：检索到的段落里有多少是真正相关的、相关段落是否都找到了——抓检索侧。
- **引用正确率**：标注 [1] 的论断与 [1] 号 chunk 的实际内容是否匹配——抓引用造假。

LLM-as-judge 的坑要管住：裁判模型有位置偏好、偏爱长答案、可能自己产生幻觉。对策：裁判用强模型、给明确的评分 rubric、关键指标抽样人工复核校准。

## 流程化

- 每次改动管道任何一层，跑一遍分层指标，输出对比报告——这是你的"回归测试"；
- bad case 自动入库：线上用户点踩/纠正的案例，脱敏后进评测集，评测集就是产品的"错题本"；
- 指标只用于**相对比较**（改动前后、A vs B 组件），绝对分数意义有限。

## 小结

评估不是上线后的选修课，是开发前的第一步。评测集 + 分层指标 + 回归流程，这三件套是后面所有章节（诊断、生产化、进阶方向）的安全网。下一篇：当指标告诉你"坏了"，怎么快速定位坏在哪层。
