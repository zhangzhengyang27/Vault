把"帮我把这 50 份简历按岗位匹配度排序"交给 Agent，它面对的第一件事不是工具调用，而是**规划**：这件事分几步、每步要什么。规划能力是 Agent 与"单轮问答"的分水岭，也是长任务失败的第一现场。

## 三种规划范式

**1. 走一步看一步（ReAct：推理-行动交替）。** 每一步模型输出"思考 + 行动"，看到行动结果再想下一步。

- 优点：零前置成本，能根据反馈随时转向，实现最简单（本站通识库第 7 篇的循环即是）。
- 失败模式：**无全局观**。第 30 步时，模型往往忘了第 1 步定的方向；容易在两个工具之间来回打转（死循环）。
- 适用：步骤数少（<10）、探索性强、每步结果决定下一步的任务。

**2. 先立计划再执行（Plan-and-Execute）。** 开局让模型产出完整计划（步骤清单），然后逐步执行，执行器只管干活。

- 优点：全局结构稳定，计划可以给人类预审（生产环境的巨大优点），步骤可并行。
- 失败模式：**计划赶不上变化**。第 3 步发现前提不成立，整份计划作废，而执行器还在闷头走。
- 适用：流程可预知、步骤间依赖清晰的批量任务（批量处理、数据搬运）。

**3. 计划随执行修订（Planner-Executor + Replan）。** 计划器产出计划，执行器干活，每完成一步（或遇错时）回到计划器修订剩余步骤。

- 优点：兼顾全局与灵活——生产级长任务 Agent 的主流形态。
- 失败模式：**过度修订**。每次小挫折都重排整个计划，摇摆不定。需要修订触发条件（只在失败/新信息出现时 replan）。

## 分解的质量决定一切

任务分解的常见毛病与对策：

- **粒度失衡**："处理这批简历"不是一步，"逐份读取"也不是好步骤。好步骤的标准：**一次工具调用可完成、结果可验证**。
- **隐式依赖没说破**：步骤 5 用到步骤 2 的输出，但计划里没写。计划输出格式里强制每个步骤声明"依赖哪些前序产物、产出什么"，下游才接得上。
- **没有完成标准**：每步和整体都要能回答"怎么算做完了"。不可验证的步骤会在后续膨胀成空转。

## 工程上的三个实用件

1. **计划外置化**：计划不是只活在对话里——写成结构化状态（JSON 步骤表：内容/状态/产出引用），跨窗口可恢复，人可审批可干预。这是"计划执行分离"在工程上的真正含义。
2. **步数与预算上限**：给循环硬性封顶（最大步数、最大 token、最大耗时），到顶就走降级路径（保存进展+请求人工）。长任务没有封顶等于定时炸弹。
3. **里程碑重述**：每完成 N 步，把"目标+已完成+剩余"压缩重述进上下文，对抗长任务的遗忘（与第 10 篇上下文工程联动）。

## 判断题：你的任务需要哪种规划

- 步骤可数、流程稳定 → 固定工作流，别引入规划器；
- 每步结果决定下一步 → ReAct，但加步数上限；
- 长任务、要人审、会变化 → Plan-and-Execute + Replan，计划外置化。
