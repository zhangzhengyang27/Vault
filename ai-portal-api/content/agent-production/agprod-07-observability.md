Agent 系统的故障排查有一个铁律：**没有轨迹的失败无法诊断**。聊天应用坏了顶多看输入输出；Agent 坏了，你要知道它在几十步里"想了什么、调了什么、拿到什么、为什么没刹车"。这一篇讲生产 Agent 的观测基建。

## 轨迹记录：记什么

一次完整的运行（run）应能还原出四样东西：

1. **决策序列**：每步模型的输入（截断存储的上下文快照）与输出（思考+动作选择）；
2. **工具调用**：工具名、参数、返回摘要、耗时、错误分类；
3. **状态变化**：计划修订、工作记忆的记账本变化（第 4 篇）、关键中间产物的引用；
4. **预算消耗**：累计 token、外部调用次数、花费——成本异常是比错误更常见的生产信号。

存储原则：**内容大而全的放对象存储，轨迹里存引用与摘要**。全量上下文直接进日志既贵又泄密（第 9 篇）。

## 追踪：把调用链串起来

Agent 一次运行背后是几十次模型调用、若干工具执行、可能的子 Agent 递归。分布式追踪的标准做法完全适用：

- **run_id 贯穿**：每次运行生成唯一 ID，所有日志、token 消耗、错误上报都带上；多智能体场景再加 parent/child 关系；
- **span 结构**：每个模型调用/工具执行是一个 span（开始/结束/状态），树状组织——火焰图一看便知"时间花在哪、钱花在哪"；
- **关联业务标识**：run_id 关联用户请求 ID、工单 ID——从用户投诉反查轨迹是最高频的排查动线。

现成工具（LangSmith、Langfuse、OpenTelemetry 方案等）都做这一层；自研时按 OpenTelemetry 的 span 模型埋即可，别发明私有格式。

## 回放与聚类：把个案变成系统知识

**回放（replay）**：拿到失败 run 的完整轨迹，能离线重演——替换模型重跑、改工具返回重跑、对照"如果第 5 步没走错会怎样"。回放是验证修复的唯一手段：改了提示词/工具/流程，把历史失败集跑一遍看通过率（与第 6 篇评测联动）。

**聚类（failure clustering）**：单看一个失败像偶然，聚起 50 个失败就看到模式。按"失败步骤+错误分类"聚类，典型产出如："38% 的失败集中在'表格解析'工具返回超长被截断后模型瞎编"——这就是系统改进的优先级清单。每周自动出一份聚类报告，比逐个看 case 高效一个量级。

## 埋点清单（从第一天就上）

- [ ] run_id / parent_run_id 贯穿
- [ ] 每步决策：模型版本、温度、上下文摘要 hash、输出动作
- [ ] 工具调用：名称、参数摘要、状态、耗时、错误分类
- [ ] token 与费用：按 run 汇总，按用户/任务类型可分组
- [ ] 用户信号：点赞/点踩、纠正、放弃率——与 run_id 关联
- [ ] 采样策略：全量记元数据，全量上下文按比例采样存储

## 与报警的关系

观测的终点是报警。Agent 系统值得配的基础告警：完成率跌破基线、单 run 成本/步数 P95 异常、特定错误类型突增（如工具鉴权失败）、死循环检出（同工具同参数连续 N 次）。别等用户来当监控。

## 小结

轨迹（看清发生了什么）→ 追踪（串起调用链）→ 回放（验证修复）→ 聚类（从个案到模式）。这四件事建起来，Agent 的生产运维就从"玄学"变成"工程"。下一篇讲失败本身：不可规避的失败如何恢复、如何兜底。
